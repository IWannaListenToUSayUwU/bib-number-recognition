# 馬拉松號碼牌影像辨識：實驗報告

日期：2026-11-12

## 1. 結論

| 項目 | 結果 |
|---|---|
| 最終方法 | YOLO11s 人物偵測 + ByteTrack 追蹤 → 軀幹裁切 → RapidOCR（PP-OCRv4）→ 軌跡加權投票 + 子字串合併 |
| test 集（9 段、50 個標註確定可讀的號碼） | **精確率 0.78／召回率 0.58／F1 0.67**（以片段為單位 bootstrap 的 95% CI：P 0.64–0.95、R 0.43–0.74、F1 0.57–0.72） |
| 嚴格計分（無法驗證的預測也算錯） | 精確率 0.66／召回率 0.58／F1 0.62 |
| 以「所有可見號碼牌」為分母（估計值） | 召回率約 0.15（29 / 約 200）。200 是 sure + partial 樣式 + unreadable 的合計，可能重複計算，只能當量級參考 |
| 速度（2 核 CPU、無 GPU、每秒取 8 格） | 處理時間為影片長度的 6–46 倍，依片段實測：v1 6／8／16 倍，v3 19／27／29 倍，v2 27／42／46 倍（與路邊觀眾、人群數量成正比） |

換句話說，系統輸出的號碼約有八成是對的；標註確定可讀的號碼約讀出六成。這是**初步、量級正確**的估計：test 只有 50 個號碼，各影片只有 10–24 個，不足以比較影片之間的差異，也不能當作正式的準確率。

### 各影片表現（test，寬鬆計分）

| 影片 | 場景 | N | 精確率 | 召回率 | F1 |
|---|---|---|---|---|---|
| v1 | 林道、強逆光、跑者稀疏 | 24 | 1.00 | 0.54 | 0.70 |
| v2 | 拱門終點、人潮極密、遮擋嚴重 | 16 | 0.88 | 0.44 | 0.58 |
| v3 | 街道側拍、號碼牌較大 | 10 | 0.56 | 0.90 | 0.69 |

各影片的 N 都很小，只能看出大致趨勢。v3 的 8 個誤報中有 4 個是「53」（很可能是路邊車牌 GU53），v3 的精確率主要由這一項決定。v3 的 3 段 test 合計只有 10 個確定號碼，其中兩段各只有 1–2 個。

## 2. 評估設計（先定規則，後看結果）

1. **片段抽樣**：先每 5 秒偵測一次人數，算出各時段的活動度；再依活動度分低、中、高三層，以固定亂數種子（20261111）抽出 dev 與 test 片段，每支影片 dev、test 各 3 段。dev 和 test 至少相隔 2 分鐘；開發期間看過的畫面一律只能進 dev。test 時段抽出後立即鎖定（work/split.json）。
2. **標準答案**：用每秒 2 格、裁切放大過的畫面，由獨立的子 agent 標註。標註員看不到系統輸出，看不清的位數一律寫 `?`。
   - dev：6 段雙標。在「確定」的號碼中，31 個裡有 28 個兩人一致。
   - test：9 段中有 6 段只有一位標註員，另外 3 段雙標，雙標的「確定」號碼 31 個裡有 27 個一致（約 87%）。6 段單標的標準答案沒有交叉驗證，也沒有人類驗證。
   - 不一致的號碼由主執行者回看原格裁定。test 預測當時已經跑完並存檔（03:27），裁定在 03:43 寫入；主執行者在裁定前沒有讀過預測結果，但這一點只能自我陳述。4 項裁定的方向都對系統不利（3 個改成 sure，最後都變成漏讀）。
3. **計分**：號碼必須完全相同，而且時間落在標註出現區間 ±2 秒內才算對。同一號碼重複輸出算誤報。與 partial 標註相容的預測，寬鬆模式下不計分，嚴格模式下算誤報。
4. **設定鎖定**：在任何 test 標註產生之前，就把參數寫入 work/FROZEN_CONFIG.json，並記錄程式碼的 sha256（work/FROZEN_CONFIG.sha256）。最終評估前驗證雜湊一致，test 只評估一次。
5. **監督**：獨立的監督 agent 在實驗前審查計畫、在結束後審查報告。已採納的修正：時間對齊計分、雙分母、test 先鎖定、以片段為單位的信賴區間。**未做到的**：test 號碼數遠低於建議的 150；R2 檢查點「完美裁切下的單張 OCR 上限」沒有單獨量測，改用「時間窗內是否讀到過正確號碼」的候選召回率來診斷。

## 3. 方法探索紀錄（dev 集）

| 嘗試 | dev 結果 | 判定 | 原因 |
|---|---|---|---|
| 整張畫面直接 OCR | 幾乎讀不到 | 淘汰 | 號碼牌只有 25–60 px |
| RBNR 號碼牌偵測器（YOLOv4-tiny，ericBayless/bib-detector）+ RapidOCR／EasyOCR／SVHN | F1 ≤ 0.17 | 淘汰 | 在人物裁切上幾乎不觸發；v1 的白底紅字完全偵測不到；整張畫面則會誤抓字幕和計時器 |
| 白色矩形啟發式定位 | 正確號碼幾乎不出現 | 淘汰 | 多數框到臉部 |
| RapidOCR，限制放大以求速度 | 偵測率大降 | 淘汰 | 小號碼牌需要放大 |
| **人物 → 軀幹 → RapidOCR 預設（短邊放大到 736）→ 軌跡投票** | F1 0.53 | 採用 | |
| ＋子字串合併（1302 吸收 302） | F1 0.60 | 採用 | 修正少讀一位數的誤報 |
| 偵測門檻調低／CLAHE 對比增強／放大到 1024／EasyOCR | 與預設相同或更差 | 不採用 | 微型測試比較了 12 個號碼 |
| 每秒取 4 格 → 8 格，並加軌跡總分門檻 | 兩段 dev 上 F1 0.64 → 0.73 | 採用 | 只比較了 2 段（29 個號碼），可能過度擬合 |
| PARSeq（場景文字辨識） | 未測 | — | 執行從 GitHub 複製的程式碼被安全機制拒絕 |

## 4. 錯誤分析與改進方向

- **v3 重複誤報「53」**：很可能來自路邊車牌 GU53。可加入「固定位置、長時間重複出現的文字視為背景」的規則。這是 test 階段才發現的，所以沒有修改，以免污染 test。
- **v2 召回低**：人潮密集，號碼牌常被手臂、手套遮住或角度太斜；在 200 個可見號碼牌中，人眼能完整讀出的也只占少數。
- **v1 強逆光**：v1_600 這類眩光片段幾乎偵測不到文字。
- **速度**：沒有 GPU 時約為影片長度的 6–46 倍。GPU 加速未實測（YOLO 與 ONNX 模型都支援 GPU）；也可以改用每秒 4 格，速度約減半，代價是召回率下降。
- **最有潛力的升級**：用少量人工框選的號碼牌資料，微調一個專用的號碼牌偵測器，同時取代目前「人物 + 軀幹裁切」的粗定位。

## 5. 限制

- test 只有 50 個確定號碼，低於監督建議的 150。主因是標註極耗用量，中途撞到 5 小時用量上限。
- 信賴區間：以片段為單位的 bootstrap 只有 9 個片段，區間本身也不穩定；以號碼為單位的區間（final_eval_test.json）沒有考慮同片段內的相關性，偏窄，其中 v1 精確率的 [1.0, 1.0] 不具意義。
- dev 只有 48 個號碼（v1、v2）。v3 的 dev 片段因用量上限沒有標註（v3_240 本身幾乎沒有跑者），所以 v3 在 test 上是第一次被評估，沒有針對 v3 調整過。
- 標準答案由視覺語言模型標註。雙標一致率約 87–90%，仍可能有共同的誤讀。

## 6. 檔案

- `src/bibread.py`：系統主程式（命令列）。
- `src/`：實驗程式（抽樣、標註素材、抽取、聚合、評分）。
- `work/split.json`、`work/gt_*.json`、`work/labels/`：抽樣結果、標準答案與原始標註。
- `work/FROZEN_CONFIG.json`、`work/final_eval_test.json`、`work/final_preds_test.json`：鎖定設定、最終評估與預測。
- `PLAN.md`：實驗過程紀錄。`work/ANNOTATION_PROTOCOL.md`：標註規範。

# 第二輪修正（2026-11-12）

## 起因
使用者發現 demo 影片的疊字錯誤，例如號碼牌 254 的跑者被標成 667。

診斷：舊版疊字一旦讀到某個號碼，就一直掛在同一個追蹤編號上，不再驗證。ByteTrack 把編號轉給下一位跑者時，標籤也跟著轉過去。CSV 是事後投票定案的，不受影響。但同一個機制也會讓「已經提早停止辨識」的軌跡不再讀取換上來的人。

## 修正內容
1. **編號轉移偵測**（`src/extract4.py`）：持續比對軀幹 HSV 直方圖與位置。Bhattacharyya 距離 > 0.45，或中心點每格移動 > 0.8 倍框寬時，就切成新的軌跡，並重新開始辨識。
2. **固定位置文字過濾**（`src/aggregate2.py`）：同一號碼的讀數中心移動 ≤ 12 px 且持續 ≥ 2 秒，就視為背景剔除。這條規則是看到第一輪 test 的車牌誤報「53」後設計的，門檻只用 dev 決定。
3. **疊字改兩階段**（`src/bibread.py`、`src/run_parallel.py`）：先定案，再只把定案號碼畫在該軌跡實際被讀到的時間 ±1 秒內。影片內容與 CSV 一致。
4. **Windows 一鍵執行**（`一鍵執行.bat`）：建立獨立 conda 環境 `bibread`，使用 CUDA 版 PyTorch，多行程平行處理整支影片。

## 評估設計
- 第一輪 test 已經看過錯誤案例，不能再當乾淨的測試集。因此用新種子（20261112）抽出 **test2**：每支影片中、高活動度各 1 段，共 6 段，抽出即鎖定（`work/split2.json`、`split2.sha256`）。
- test2 由子 agent 標註，其中 2 段雙標。爭議在系統還沒跑 test2 之前就裁定完成，標準答案的 sha256 記錄在 `work/gt_test2.sha256`。
- dev 補標 v3_1440（單人標註）。在 dev 上調整門檻時，F1 的差異都在雜訊範圍內，所以聚合門檻維持第一輪的設定。第二版設定鎖定在 `work/FROZEN_CONFIG_v2.json`（10:58），之後 test2 只評估一次。

|---|---|---|
| v1_720 | 與 dev v1_600 結束點 660 相隔 60 秒 | v1 依規則找不到片段，自動放寬 |

## 結果

### test2（6 段、37 個確定號碼，第二版設定，只評估一次）
| | 精確率 | 召回率 | F1 | 以片段為單位 bootstrap 的 F1 95% CI |
|---|---|---|---|---|
| 全部（寬鬆計分） | 0.62 | 0.62 | 0.62 | 0.39–0.78 |
| 全部（嚴格計分） | 0.58 | 0.62 | 0.60 | — |
| 不含 v2_540 | 0.61 | 0.65 | 0.63 | 0.38–0.80 |
| v1（N=13） | 1.00 | 0.62 | 0.76 | — |
| v2（N=5） | 0.33 | 0.20 | 0.25 | — |
| v3（N=19） | 0.54 | 0.74 | 0.62 | — |

test2 的精確率比第一輪 test 低（0.62 對 0.78），主要是 v3 有 12 個誤報。車牌「53」又出現了，因為文字框位置抖動約 15–18 px，超過 12 px 門檻沒被濾掉。另外還有 339、228 各重複兩次，以及把 301 讀成 1301。

兩輪的 N 都很小（50 與 37），信賴區間大幅重疊，**不能據此說第二版變好或變差**。

### 各項修正的效果（事後分析，不是用來調參）
| 修正 | dev | test2 | 舊 test（已污染，僅供參考） |
|---|---|---|---|
| 編號轉移偵測（對 CSV） | 沒有變化 | 沒有變化 | — |
| 固定位置過濾 | 刪 1 誤報、0 誤刪 | 刪 5 誤報、誤刪 1 真號碼 | 刪 0 誤報、誤刪 1 真號碼 |

結論：編號轉移偵測對 CSV 沒有幫助，它的價值在疊字（見下）。固定位置過濾好壞參半，不是穩定的改進。

### 疊字正確率（新增指標，獨立 agent 盲檢）
在 test2 上，用同一份辨識結果分別模擬舊版和新版疊字，每秒取一格抽樣，共 89 個小圖。兩版混合打亂後交給獨立 agent，它不知道每張小圖屬於哪一版。

| | 樣本數 | 正確 | 錯誤（標錯號碼或標在沒號碼牌的人身上） | 無法判定 | 可判定者中的正確率 | 錯標率 |
|---|---|---|---|---|---|---|
| 舊版疊字 | 47 | 11 | 27 | 9 | 29% | **57%** |
| 新版疊字 | 42 | 23 | 5 | 14 | 82% | **12%** |

使用者指出的疊字問題，主要來自舊版的疊字方式，新版已大幅改善。

第一次盲檢時，我做的小圖把標籤文字截斷了，89 項全部判為無法判定，所以修正小圖後重做。廢棄的那份保留在隔離區。

## 第二輪仍未解決
- 車牌等固定文字：位置抖動，12 px 門檻抓不到。改進方向是改用「相對人物框的位置」或「完全不在任何人物軀幹內」來判斷。
- 號碼牌被遮住而少讀或多讀一位數（107 對 11?7、1301 對 301）。
- v2 密集人群的召回率很低。
- 整體最有效的升級，仍是用少量人工框選資料訓練專用的號碼牌偵測器。
